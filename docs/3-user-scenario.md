## 1. 개요

**목적:** PRD의 기능 요구사항(FR)을 사용자 행동 → 시스템 반응의 흐름으로 풀어, 인수 확인(G-01)의 수동 점검 기준으로 쓴다. 규칙·상태 정의는 재정의하지 않고 ID로 참조한다.

**ID 체계 및 표기 규칙**

| 항목 | 규칙 |
|------|------|
| 시나리오 ID | SN-xx(기능 시나리오), E2E-xx(엔드투엔드). 4장은 상태 판정 표(ST-xx 행 번호) |
| 흐름 번호 | 정상 흐름은 1, 2, 3…. 대안·예외는 분기 단계 번호 + 소문자(예: 3a)로 표기 |
| 화면 | 단계 앞 `[SC-xx]`. 로그아웃(FR-11)은 로그인 후 공통 헤더 |
| 날짜 예시 | 오늘 = 2026-11-04(수). 주 뷰는 일~토(AS-09) |
| 범위 | 기능 흐름 중심. 페르소나 서사·접근성은 다루지 않는다(PRD 3·4장) |

## 3. 시나리오 상세

공통 사전 조건: 별도 명시가 없으면 사용자는 로그인된 상태이며 BR-01, BR-02가 적용된다.

### SN-01 회원가입

**사전 조건:** 방문자(미로그인). 사용 중이지 않은 이메일.

**정상 흐름**
1. [SC-01] 이메일·비밀번호(8자 이상)·이름을 입력하고 가입을 요청한다. → 계정이 생성되고 '기본' 카테고리가 자동 생성된다(BR-06).
2. 시스템은 가입 완료 후 로그인 화면(SC-02)으로 이동한다(SA-01).

**대안·예외 흐름**
- 1a. 이미 가입된 이메일 → 가입 거부 메시지(BR-03). 계정·카테고리는 추가 생성되지 않는다.
- 1b. 이메일 형식 오류 / 비밀번호 8자 미만 / 이름 비어 있음 또는 50자 초과 → 거부(AS-08). 클라이언트 검증을 우회한 직접 요청도 서버에서 거부(FR-13).
- 1c. 필수 항목 누락 → 거부.

**기대 결과**
- 유효 입력으로 가입하면 사용자 1명과 기본 카테고리 1개가 생성된다.
- 동일 이메일 재가입 시도는 거부되고 사용자 수가 늘지 않는다.
- 1b 조건의 요청은 화면 경로와 직접 요청 모두에서 거부된다.

### SN-02 로그인 및 실패 차단

**사전 조건:** 가입된 계정(SN-01 완료). 로그아웃 상태.

**정상 흐름**
1. [SC-02] 올바른 이메일·비밀번호를 입력한다. → 로그인되고 인증 쿠키 2종(`access_token` 15분, `refresh_token` 7일, 둘 다 httpOnly, PA-01)이 설정된다.
2. 시스템은 앱 화면(할일 목록 SC-05)으로 진입시킨다(SA-02).

**대안·예외 흐름**
- 1a. 비밀번호 오류 → 실패 메시지. 1b와 동일한 문구·동작.
- 1b. 존재하지 않는 이메일 → 1a와 구분할 수 없는 동일 메시지(이메일 존재 여부 비노출).
- 1c. 같은 이메일로 연속 5회 실패 → 해당 이메일 로그인이 5분간 차단된다(NFR-11). 차단 중에는 올바른 비밀번호도 거부된다(SA-03).
- 1d. 차단 5분 경과 후 올바른 자격증명 → 로그인 성공.
- 1e. 5회 미만 실패 후 성공 → 정상 로그인(SA-03).

**기대 결과**
- 1a와 1b의 응답(메시지·상태 코드)이 동일하다.
- 5회째 실패 직후 6번째 시도(정답 포함)는 거부되고, 5분 경과 후 성공한다.
- 응답 쿠키 2종 모두에 `HttpOnly`, `SameSite=Lax`가 있다(NFR-10).
- 같은 계정으로 다른 기기에서 로그인해도 각 기기의 세션이 독립적으로 유지된다(SA-10).

### SN-03 미인증·세션 만료 접근

**사전 조건:** 쿠키가 없거나, Refresh Token이 만료(로그인 후 7일 경과)·폐기되어 갱신할 수 없는 상태.

**정상 흐름**
1. 앱 화면(예: SC-05) 주소로 직접 접근한다. → 로그인 화면(SC-02)으로 이동한다.

**대안·예외 흐름**
- 1a. 사용 중 Access Token이 만료되고 Refresh Token도 만료·폐기된 상태에서 목록 조회·저장 등 동작 → API가 미인증으로 응답하고, 클라이언트의 갱신도 실패하여 세션 만료 안내(WA-21) 후 SC-02로 이동한다(SA-11). Access Token만 만료된 경우는 SN-15를 따른다.
- 1b. 로그인 후 원래 화면 복귀 여부는 정하지 않는다(SA-04).

**기대 결과**
- 미인증/만료 상태에서 API는 데이터 없이 401로 응답하고, 앱 화면 접근은 SC-02로 이동한다(FR-02).
- Refresh Token 갱신까지 실패했을 때만 세션 만료 안내가 나온다(SA-11).
- 재로그인 후 앱 화면을 정상 사용할 수 있다.

### SN-04 로그아웃

**사전 조건:** 로그인 상태, 아무 앱 화면.

**정상 흐름**
1. [공통 헤더] 로그아웃을 선택한다. → 서버가 해당 Refresh Token을 폐기하고 인증 쿠키 2종을 만료시킨다.
2. 시스템은 로그인 화면(SC-02)을 보여준다.
3. 브라우저 뒤로가기 또는 앱 화면 주소로 접근한다. → SC-02로 이동한다(SN-03).

**대안·예외 흐름**
- 1a. 로그아웃 요청 실패(네트워크) → 로그아웃되지 않은 상태로 유지되고 오류가 표시된다(SA-05).

**기대 결과**
- 로그아웃 응답에서 인증 쿠키 2종이 만료 처리되고, 서버의 Refresh Token 행이 삭제된다.
- 로그아웃 전의 Refresh Token을 직접 요청으로 갱신(`/api/auth/refresh`)하면 401이다(서버 폐기 확인).
- 이후 앱 화면·API 접근은 모두 SC-02로 이동한다.
- 한계: 이미 발급된 Access Token은 최대 15분 유효하다(PA-01).

### SN-15 Access Token 만료 후 자동 갱신

**사전 조건:** 로그인 후 15분이 지나 Access Token이 만료되었고, Refresh Token은 유효(7일 이내)하다.

**정상 흐름**
1. [SC-05] 목록 조회·저장 등 동작을 한다. → API가 401을 반환한다.
2. 클라이언트가 `POST /api/auth/refresh`를 한 번 호출한다. → 새 Access Token과 새 Refresh Token 쿠키가 설정된다.
3. 클라이언트가 원래 요청을 한 번 재시도한다. → 정상 응답으로 화면이 유지된다.

**대안·예외 흐름**
- 1a. 동시에 여러 요청이 401을 받음 → 갱신 요청은 하나만 보내고 나머지는 그 결과를 기다린 뒤 각각 재시도한다.
- 2a. 갱신 실패(Refresh Token 만료·폐기·이미 사용됨) → 원래 401이 전달되어 SN-03 1a(세션 만료 안내 후 SC-02)로 이어진다.
- 2b. 갱신된 Refresh Token의 만료는 연장되지 않고 기존 만료 시각을 이어받는다(로그인 후 최대 7일, PA-01).

**기대 결과**
- 사용자는 로그인 화면으로 이동하지 않고 15분 경과 전후로 같은 화면을 계속 사용한다.
- 동시 401에도 갱신 요청은 1회다.
- 갱신에 사용된 이전 Refresh Token으로 다시 갱신하면 401이다(재사용 탐지 없음, PA-01).

### SN-05 내 정보 수정

**사전 조건:** 로그인 상태.

**정상 흐름**
1. [SC-03] 내 정보를 조회한다. → 이메일(읽기 전용)과 이름이 표시된다.
2. 이름을 변경해 저장한다. → 저장되고 변경된 이름이 반영된다.
3. 현재 비밀번호와 새 비밀번호(8자 이상)를 입력해 저장한다. → 비밀번호가 변경된다.
4. 로그아웃 후 새 비밀번호로 로그인한다. → 성공한다.

**대안·예외 흐름**
- 3a. 현재 비밀번호 불일치 → 변경 거부, 기존 비밀번호 유지(BR-12).
- 3b. 새 비밀번호 8자 미만 → 서버에서 거부(FR-13).
- 2a. 이름이 비어 있거나 50자 초과 → 거부(AS-08).
- 1a. 이메일 변경 시도(직접 요청 포함) → 불가(AS-05).

**기대 결과**
- 이름 변경이 재조회 시 유지된다.
- 현재 비밀번호가 맞을 때만 비밀번호가 바뀌며, 이전 비밀번호로는 로그인되지 않는다.
- 이메일은 변경되지 않는다.

### SN-06 카테고리 관리

**사전 조건:** 로그인 상태. '기본' 카테고리와 사용자 카테고리 '업무'(할일 2건 소속)가 있다.

**정상 흐름**
1. [SC-04] 새 카테고리 '학교'(1~20자)를 등록한다. → 목록에 추가된다.
2. '학교' 이름을 '과제'로 수정한다. → 변경이 반영된다.
3. '업무'를 삭제하고 확인 다이얼로그에서 확인한다(`4-wireframe.md` WA-08). → 카테고리가 삭제되고 소속 할일 2건은 삭제되지 않고 '기본' 카테고리로 이동한다(BR-10).
4. [SC-05] 기본 카테고리로 필터한다. → 이동된 2건이 나타난다.

**대안·예외 흐름**
- 1a. 이미 있는 이름 등록 → 거부(BR-09). 2a. 다른 카테고리와 같은 이름으로 수정 → 거부.
- 1b. 이름이 비어 있거나 20자 초과 → 서버에서 거부(FR-13).
- 2b. 기본 카테고리 이름 변경 시도 → 거부(BR-08).
- 3a. 기본 카테고리 삭제 시도 → 거부(BR-08). 기본 카테고리와 그 할일은 변함없다.
- 3b. 다른 사용자의 카테고리 ID 접근 → 없는 ID와 동일하게 처리(BR-02, SA-06).
- 3c. 확인 다이얼로그에서 취소 → 카테고리와 소속 할일 모두 변화 없음.

**기대 결과**
- 삭제된 카테고리의 할일 수 = 기본 카테고리로 이동된 수이며 할일 총수는 변하지 않는다.
- 기본 카테고리는 수정·삭제 시도 후에도 그대로 존재한다.

### SN-07 할일 등록

**사전 조건:** 로그인 상태. 카테고리 '기본', '업무'가 있다.

**정상 흐름**
1. [SC-06] 제목 '보고서 작성', 시작일 2026-11-05, 종료일 2026-11-07(date picker 선택), 카테고리 '업무'를 입력해 저장한다. → 할일이 생성된다.
2. [SC-05] 목록에서 확인한다. → 해당 할일이 '업무'로, 상태 '시작 전'(오늘 11-04, 4장)으로 표시된다.
3. 카테고리를 선택하지 않고 같은 방식으로 등록한다. → '기본' 카테고리에 속한다(BR-07).

**대안·예외 흐름**
- 1a. 제목·시작일·종료일 중 하나라도 비어 있음 → 저장되지 않음(BR-04).
- 1b. 종료일 < 시작일(예: 시작 11-07, 종료 11-05) → 거부 메시지(BR-05).
- 1c. 종료일 = 시작일 → 저장 허용.
- 1d. 제목 0자 또는 101자 이상 → 서버에서 거부(AS-08, FR-13).
- 1e. 타인의 카테고리 ID 지정(직접 요청) → 거부(BR-02, SA-06).

**기대 결과**
- 유효 입력은 목록·캘린더에 나타나고, 1a·1b·1d는 할일 수가 늘지 않는다.
- 하루짜리(1c)는 저장되어 시작일 당일 '진행중'으로 판정된다(4장 ST-05).
- 미선택 시 소속 카테고리는 '기본'이다.

### SN-08 할일 수정

**사전 조건:** 본인 할일 1건(제목 '보고서 작성', 11-05~11-07, '업무').

**정상 흐름**
1. [SC-05] 할일을 선택한다. → [SC-06] 편집 화면에 현재 값이 채워져 표시된다.
2. 제목·기간·카테고리·완료 여부를 변경해 저장한다. → 변경이 저장된다.
3. [SC-05] 목록으로 돌아가 변경값과 변경된 상태를 확인한다.

**대안·예외 흐름**
- 2a. 종료일 < 시작일, 필수 항목 비움, 길이 초과 → SN-07 1a·1b·1d와 같은 검증으로 거부(FR-08, FR-13).
- 2b. 카테고리를 '선택 안 함'으로 변경 → '기본'에 속한다(BR-07).
- 2c. 기간 변경으로 오늘이 기간 밖이 됨 → 4장 규칙으로 상태가 재판정된다(BR-13).
- 1a. 타인 할일 → SN-13.

**기대 결과**
- 재조회 시 변경값이 유지된다. 거부된 수정은 기존 값을 바꾸지 않는다.
- 기간 변경 후 상태는 4장 표와 일치한다.

### SN-09 할일 완료 처리·해제

**사전 조건:** 미완료 할일 1건(예: 11-04~11-06).

**정상 흐름**
1. [SC-05] 완료 토글을 켠다. → 상태가 '완료'가 된다.
2. 상태 필터 '완료'를 선택한다. → 해당 할일이 나타난다.
3. 완료 토글을 끈다. → 오늘 날짜 기준으로 재판정된다(4장).

**대안·예외 흐름**
- 1a. 기간 시작 전(오늘 < 시작일) 완료 처리 → '완료'(ST-08).
- 3a. 기한이 지난 할일의 완료 해제 → '기한 초과'(ST-10).
- 3b. 해제 후 '완료' 필터 → 목록에서 사라진다.

**기대 결과**
- 완료 시 날짜와 무관하게 '완료', 해제 시 시작일·종료일·오늘로 재판정된다(ST-08, ST-10~ST-12).
- 새로고침 후에도 완료 여부가 유지된다.

### SN-10 할일 삭제

**사전 조건:** 본인 할일 1건.

**정상 흐름**
1. [SC-05] 삭제를 선택한다. → 확인 절차가 표시된다(BR-11).
2. 확인한다. → 영구 삭제되고 목록에서 사라진다.
3. [SC-07] 캘린더를 확인한다. → 해당 기간 날짜에서도 사라져 있다.

**대안·예외 흐름**
- 2a. 확인 절차에서 취소 → 삭제되지 않고 목록·캘린더에 그대로 있다.
- 2b. 삭제된 할일 ID로 재접근 → 404(복구 불가, AS-07).

**기대 결과**
- 확인 전에는 삭제되지 않는다. 취소 시 할일 수가 변하지 않는다.
- 확인 후 목록·캘린더·직접 조회 모두에서 없다.

### SN-11 할일 목록 조회·필터

**사전 조건:** 오늘 2026-11-04. 카테고리 '업무', '기본'에 시작 전·진행중·완료·기한 초과 할일이 각 1건 이상 있다.

**정상 흐름**
1. [SC-05] 목록을 연다. → 클라이언트가 오늘(2026-11-04)을 전달하고(PA-06), 종료일 오름차순(같으면 생성일시, 그래도 같으면 ID 오름차순)으로 최대 50건이 표시된다.
2. 상태 필터 '진행중'을 선택한다. → 4장 판정으로 진행중인 할일만 표시된다.
3. 카테고리 필터 '업무'를 추가한다. → 두 조건의 AND 결과만 표시된다(AS-06).
4. 상태 필터를 '기한 초과'로 바꾼다. → 상태는 한 번에 하나만 적용된다.

**대안·예외 흐름**
- 2a. 조건에 맞는 할일 없음 → 빈 목록이 표시된다(문구는 SA-07).
- 1a. 할일이 51건 이상 → 첫 페이지는 50건. 다음 건은 이후 페이지에서 조회된다(이동 방식은 SA-08).
- 1b. 날짜가 바뀐 뒤(예: 11-05) 다시 조회 → 새 '오늘'로 재판정된다.
- 1c. 타 사용자 할일은 어떤 필터에서도 나타나지 않는다(BR-02).

**기대 결과**
- 각 필터 결과가 4장 표의 판정과 일치하고 모든 할일은 정확히 하나의 상태에 속한다.
- 목록은 종료일 오름차순, 종료일이 같으면 생성일시 오름차순, 그래도 같으면 ID 오름차순이다(PRD FR-06).
- 페이지당 50건을 넘지 않는다.

### SN-12 캘린더 조회(월/주/일)

**사전 조건:** 오늘 2026-11-04. 할일 A(11-02~11-04), B(11-06~11-10, 미완료), C(10-28~11-03, 미완료).

**정상 흐름**
1. [SC-07] 월 뷰(2026-11)를 연다. → 뷰 범위와 기간이 겹치는 할일이 기간을 잇는 막대로 표시된다.
2. 주 뷰(2026-11-01~11-07, 일~토)로 전환한다. → 해당 7일과 겹치는 할일만 표시된다.
3. 일 뷰(2026-11-04)로 전환한다. → 11-04가 기간에 포함된 할일 목록(A)이 표시된다.
4. 각 할일의 상태 표시를 확인한다. → 상태별 표시가 서로 다르다(7장). 판정 기준일은 클라이언트가 전달한 오늘이다(PA-06).

**대안·예외 흐름**
- 2a. 이전/다음 이동으로 범위가 바뀜 → 새 범위와 겹치는 할일만 조회된다(NFR-04).
- 1a. 기간이 뷰 범위와 일부만 겹침 → 겹친 날짜에만 표시(4장 표 B절 참조).
- 1b. 범위 안에 할일이 없음 → 빈 캘린더(SA-07).
- 3a. 완료 처리된 할일은 해당 기간 날짜에서 '완료' 표시로 나타난다.

**기대 결과**
- 할일은 시작일~종료일 모든 날짜에 표시되고, 범위 밖 날짜에는 표시되지 않는다.
- 위 데이터에서 월 뷰(11월)의 C는 11-01~11-03에만 표시된다. 주 뷰의 B는 11-06~11-07에만 표시된다.
- 일 뷰 11-04: A는 표시, B·C는 미표시.

### SN-13 타인 할일 접근 차단

**사전 조건:** 사용자 U1, U2가 있고 U2에게 할일 ID=T2가 있다. U1로 로그인.

**정상 흐름**
1. U1이 T2의 ID로 조회·수정·완료 처리·삭제를 각각 요청한다(직접 URL 또는 직접 요청). → 모두 404가 반환된다.
2. 존재하지 않는 ID(예: 999999)로 같은 요청을 한다. → 1의 응답과 동일한 404다.
3. U2로 로그인해 T2를 확인한다. → T2는 변경 없이 그대로 있다.

**대안·예외 흐름**
- 1a. UI에서 타인 ID 화면(SC-06) 직접 진입 → '찾을 수 없음' 처리(문구는 SA-06).
- 1b. 본인 할일을 타인 카테고리로 이동하는 등 타인 소유 데이터 참조 → 거부(BR-02).

**기대 결과**
- 타인 ID와 없는 ID의 응답(상태 코드·본문 형식)이 같아 존재 여부를 알 수 없다(NFR-06).
- 어떤 요청도 U2의 데이터를 변경하지 않는다.

### SN-14 할일 메모 입력·수정·표시

**사전 조건:** 로그인 상태. FR-12는 P1이므로 구현 시에만 점검한다.

**정상 흐름**
1. [SC-06] 할일 등록 시 메모를 입력해 저장한다. → 메모가 저장된다.
2. 편집 화면에서 메모를 수정해 저장한다. → 수정된 메모가 저장된다.
3. 할일을 다시 열어 확인한다. → 메모가 표시된다.

**대안·예외 흐름**
- 1a. 메모 1,001자 이상 → 서버에서 거부(AS-08, FR-13).
- 1b. 메모를 비워 둠 → 저장 허용(필수 아님, BR-04).

**기대 결과**
- 1,000자 메모는 저장·표시되고 1,001자는 거부된다.
- 메모 수정 후 재조회 시 변경값이 유지된다.

### E2E-02 공용 PC 사용 후 로그아웃

| 단계 | 사용자 행동 → 시스템 반응 | 화면 |
|------|--------------------------|------|
| 1 | 할일 목록 확인 및 사용 | SC-05 |
| 2 | 공통 헤더에서 로그아웃 → Refresh Token 서버 폐기, 쿠키 2종 만료, 로그인 화면 표시 | SC-02 |
| 3 | 다음 사용자가 브라우저 뒤로가기 → 로그인 화면으로 이동, 이전 사용자의 할일 미노출 | SC-02 |
| 4 | 앱 화면 주소로 직접 접근 → 로그인 화면으로 이동 | SC-02 |

**기대 결과**
- 로그아웃 후 이전 사용자의 할일·카테고리·내 정보가 어떤 화면에도 표시되지 않는다.
- 로그아웃 응답에서 인증 쿠키 2종이 만료되고 Refresh Token이 서버에서 폐기된다(FR-11).
- 한계: 이미 발급된 Access Token은 최대 15분 유효하다(PA-01).

## 6. 가정·미결 사항

| ID | 구분 | 내용 |
|----|------|------|
| SA-01 | 가정 | 가입 성공 후 자동 로그인하지 않고 로그인 화면(SC-02)으로 이동한다. (문서에 가입 후 동작 미정의) |
| SA-02 | 가정 | 로그인 후 첫 화면은 할일 목록(SC-05)이다. |
| SA-03 | 가정 | 로그인 실패 횟수는 이메일 단위로 집계하며, 존재하지 않는 이메일도 동일하게 집계·차단한다(존재 여부 비노출). 성공 로그인 시 횟수는 초기화되고, 차단 중에는 정답도 거부한다. |
| SA-04 | 가정 | 세션 만료 후 재로그인 시 원래 화면으로 복귀하지 않으며 기본 첫 화면으로 간다. |
| SA-05 | 가정 | 로그아웃 요청 실패 시 로그인 상태가 유지되고 오류가 표시된다. |
| SA-06 | 가정 | 타인의 카테고리·할일 ID 접근은 모두 없는 ID와 동일한 404로 처리한다(NFR-06은 모든 데이터 접근에 적용). UI의 '찾을 수 없음' 처리는 `4-wireframe.md` 5.7을 따른다. |
| SA-07 | 가정 | 결과가 없을 때의 빈 목록·빈 캘린더 안내 문구는 `4-wireframe.md` 5.6을 따른다. |
| SA-08 | 가정 | 51건 이상일 때 페이지 이동 UI는 `4-wireframe.md` 5.5를 따른다. 시나리오는 첫 페이지 50건만 검증한다. |
| SA-09 | 가정 | 할일 저장 후 목록(SC-05)으로 복귀한다. 이 복귀는 G-04 측정 구간(PRD G-04: SC-01 진입~첫 할일 저장) 밖이므로 전환 수에 포함하지 않는다. |
| SA-10 | 가정 | 여러 기기에서 동시에 로그인할 수 있으며 로그인마다 Refresh Token이 1개 발급된다. 한 기기의 로그아웃은 해당 기기의 Refresh Token만 폐기한다. |
| SA-11 | 가정 | 세션 만료 안내(WA-21)는 Access Token 만료가 아니라 Refresh Token 갱신까지 실패했을 때만 표시한다. 이미 인증된 상태가 아니면(미로그인 접근) 안내 없이 SC-02로 이동한다. |
| 참조 | 미결 | 도메인 OQ-01(회원 탈퇴), OQ-02(비밀번호 찾기/재설정)는 본 문서 범위 밖이다. |
