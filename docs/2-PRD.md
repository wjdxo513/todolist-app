## 1. 개요

**제품 목적:** 인증된 사용자가 할일을 카테고리와 기간(시작일~종료일)으로 관리하고 월/주/일 캘린더에서 조회하는 웹 앱을 2일 내 핵심 기능 중심으로 출시한다.

| 배경 | 내용 |
|------|------|
| P1 | 사용자 개인별 할일 관리 앱 부재 |
| P2 | 시작일·종료일(기간) 기능 필요 |
| P3 | 월·주·일 캘린더 일괄 조회 필요 |

## 5. 기능 요구사항

우선순위: **P0** = 2일 내 필수 / **P1** = 여유 시 / 범위 외 = 4장 제외 항목. 공통: 모든 사용자 기능에 BR-01, BR-02 적용.

| ID | 우선순위 | 요구사항 | 관련 F / UC / BR | 인수 기준 |
|----|----------|----------|------------------|-----------|
| FR-01 | P0 | 회원가입 | F1 / UC-01 / BR-03, BR-06 | 유효한 이메일·비밀번호·이름으로 가입되고 '기본' 카테고리가 자동 생성된다. 중복 이메일은 거부된다. |
| FR-02 | P0 | 로그인·세션 유지 | F1 / UC-02 / BR-01, BR-03 | 올바른 자격증명이면 로그인되어 앱 화면에 진입한다. 잘못되면 실패 메시지를 보이되 이메일 존재 여부는 구분하지 않는다. Access Token이 만료되어도 Refresh Token이 유효하면 클라이언트가 자동 갱신해 화면이 유지된다. 미인증 또는 세션 만료(Refresh Token 만료·폐기, PA-01) 상태에서 API는 401(미인증)로 응답하고, 앱 화면 접근 시 로그인 화면으로 이동한다. |
| FR-03 | P0 | 내 정보 조회·수정(이름, 비밀번호) | F3 / UC-04 / BR-12 | 이름 변경이 저장·반영된다. 비밀번호는 현재 비밀번호가 맞을 때만 변경된다. 이메일은 수정할 수 없다(AS-05). |
| FR-04 | P0 | 카테고리 등록·수정·삭제 | F2 / UC-05 / BR-08, BR-09, BR-10 | 같은 이름은 거부된다. 기본 카테고리는 수정·삭제할 수 없다. 삭제 시 소속 할일이 기본 카테고리로 이동한다. |
| FR-05 | P0 | 할일 등록 (제목, 카테고리, 시작일·종료일 date picker 선택) | F2, F4 / UC-06 / BR-04, BR-05, BR-07 | 제목·시작일·종료일 없이는 저장되지 않는다. 종료일<시작일이면 거부된다. 같은 날은 허용된다. 카테고리 미선택 시 기본에 속한다. |
| FR-06 | P0 | 할일 목록 조회 및 필터(카테고리, 상태 1개) | F5 / UC-07 / BR-13 | 상태 필터(시작 전/진행중/완료/기한 초과)는 도메인 4장 판정과 일치하며, 판정 기준일은 클라이언트가 보낸 '오늘'이다(PA-06). 카테고리와 상태 필터는 AND로 적용된다. 기본 정렬은 종료일 오름차순, 같으면 생성일시 오름차순, 그래도 같으면 ID 오름차순이며 페이지당 50건이다(페이지 경계 중복·누락 방지, `7-erd.md` ER-05). |
| FR-07 | P0 | 할일 완료 처리 / 해제 | F5 / UC-09 / BR-13 | 완료 처리하면 '완료' 필터에 나타나고, 해제하면 날짜 기준 상태로 재판정된다. |
| FR-08 | P0 | 할일 수정 (편집 화면) | F7 / UC-08 / BR-04, BR-05, BR-07 | 제목·기간·카테고리·완료 여부 변경이 저장되며 FR-05와 같은 검증이 적용된다. 타인 할일은 수정할 수 없다. |
| FR-09 | P0 | 할일 삭제 | F6 / UC-10 / BR-11 | 확인 절차 후에만 영구 삭제되고 목록·캘린더에서 사라진다. 취소하면 유지된다. |
| FR-10 | P0 | 월·주·일 캘린더 조회 | F8 / UC-11 / BR-13 | 뷰 범위(월/주/일)와 기간이 겹치는 할일만 조회된다. 할일이 기간 내 모든 날짜에 표시되고 일부만 겹치면 겹친 날짜만 표시된다(도메인 7장). 각 할일의 상태가 서로 다르게 표시된다(판정 기준일 PA-06). 주는 일~토. |
| FR-11 | P0 | 로그아웃 | (원문 외) / UC-03 / BR-01 | 로그아웃하면 서버가 Refresh Token을 폐기하고 인증 쿠키 2종을 만료시키며, 폐기된 Refresh Token으로는 갱신되지 않고(401), 이후 API는 401로 응답하며 앱 화면 접근 시 로그인 화면으로 이동한다. |
| FR-12 | P1 | 할일 메모(최대 1,000자) | (원문 외) / UC-06, UC-08 / AS-10 | 메모가 저장·수정·표시된다. |
| FR-13 | P0 | 입력값 검증 | F1~F8 / 전 UC / BR-04, AS-08 | AS-08의 길이·형식 기준을 벗어난 입력은 클라이언트 검증과 무관하게 서버에서 거부된다. |

## 6. 비기능 요구사항

수치는 모두 **가정**이며 부하 테스트 결과에 따라 조정한다.

| ID | 구분 | 요구사항 | 목표값 (가정) | 검증 방법 |
|----|------|----------|---------------|-----------|
| NFR-01 | 성능·동시성 | PA-07 조건(가상 사용자 1000명, 요청 간 대기 5~10초)에서 일반 API(조회·등록·수정·삭제) 응답시간 | p95 ≤ 500ms | k6로 램프업 2분 + 유지 10분 |
| NFR-02 | 성능·동시성 | 동일 조건에서 에러율(5xx·타임아웃) | ≤ 1% | 동일 부하 테스트 |
| NFR-03 | 성능·동시성 | 로그인·가입(비밀번호 해시 포함) 응답시간 | p95 ≤ 1,500ms | 동일 부하 테스트 |
| NFR-04 | 성능·동시성 | 최소 수단: DB 커넥션 풀, 소유자·기간 컬럼 인덱스, 캘린더는 뷰 범위 기간만 조회, 목록은 페이지당 50건 | 단일 서버 1대 기준 달성 | 설계·코드 리뷰, NFR-01 결과 |
| NFR-05 | 보안 | 비밀번호는 단방향 해시(PA-02) 저장, 평문 저장·로그 금지 | 100% | 코드 리뷰 |
| NFR-06 | 보안 | 모든 데이터 접근은 소유자 검증, 타인 데이터는 존재 여부 비노출(BR-02) | 타인 ID 접근 시 없는 ID와 동일한 404 응답 | API 테스트 |
| NFR-07 | 보안 | SQL은 파라미터 바인딩만 사용(SQL 인젝션 방지) | 100% | 코드 리뷰 |
| NFR-08 | 반응형 | 모바일~데스크톱 폭에서 핵심 화면이 깨지지 않고 사용 가능 | 360px 이상 | 브라우저 개발자 도구 수동 확인 |
| NFR-09 | 브라우저 | 최신 Chrome, Edge, Safari, Firefox 지원 (가정) | 최신 2개 버전 | 수동 확인 |
| NFR-10 | 보안 | 인증 쿠키 2종(`access_token`, `refresh_token`)은 `HttpOnly`, `SameSite=Lax`, 운영 환경 `Secure`(HTTPS). Access Token은 `HS384` 외 알고리즘(`none` 포함)을 거부한다. 상태 변경은 GET이 아닌 메서드만 사용, CORS는 프론트엔드 출처만 허용 | 100% | 응답 헤더 확인 |
| NFR-11 | 보안 | 같은 이메일로 로그인 연속 실패 시 일시 차단(무차별 대입 방지) | 5회 실패 시 5분 차단 | API 테스트 |
| NFR-12 | 운영 | 서버 에러(5xx)는 요청 경로·시각과 함께 로그로 남긴다. 비밀번호·토큰은 로그에 남기지 않는다 | 100% | 로그 확인 |

## 11. 가정·미결 사항

| ID | 구분 | 내용 |
|----|------|------|
| PA-01 | 가정 | 인증은 AS-05(이메일·비밀번호)를 따르고, 세션 유지는 Access Token과 Refresh Token 쿠키 2종으로 한다. Access Token은 JWT(`HS384`), 만료 15분. Refresh Token은 JWT가 아닌 불투명 난수 문자열이며 DB에는 해시만 저장하고, 만료는 발급(로그인) 시점부터 7일 절대 만료로 이 기간이 세션 유지 기간이다. 갱신 시 Refresh Token을 교체(rotation)하되 만료는 기존 값을 이어받는다. 근거: 서버가 세션을 폐기할 수 있으면서 Access Token 검증은 DB 조회 없이 처리한다. 한계: 이미 발급된 Access Token은 로그아웃·폐기 후에도 최대 15분 유효하다. 재사용 탐지(토큰 계열 폐기)는 하지 않으며, 이미 사용된 Refresh Token은 행이 없어 401이 될 뿐이다. |
| PA-02 | 가정 | 비밀번호 해시는 bcrypt 계열을 사용한다. |
| PA-03 | 가정 | 6장의 성능 수치(p95 500ms, 에러율 1%, 요청 간격 5~10초)는 합리적 추정이며 확정값이 아니다. 1000명은 '동시 접속' 기준이며 요청량은 약 100~200 RPS로 추정한다. |
| PA-04 | 가정 | 우선순위 하향: 메모만 P1이다(원문 외, AS-10). 로그아웃도 원문 외지만 공용 PC 사용과 httpOnly 쿠키 특성상 P0로 둔다. |
| PA-05 | 가정 | 목록 페이지당 50건, 일정·부하 환경은 단일 서버 기준이다. |
| PA-06 | 가정 | 상태 판정 기준일 '오늘'(AS-02)은 클라이언트가 목록·캘린더 조회 시 로컬 날짜(YYYY-MM-DD)로 서버에 전달하고, 서버는 그 값으로 상태 필터를 적용한다. |
| PA-07 | 가정 | 부하 테스트 조건: 시드 데이터 사용자 1,000명 × 할일 200건 × 카테고리 5개. 요청 비율은 목록·캘린더 조회 70%, 할일 등록·수정·완료·삭제 25%, 로그인 5%. 가상 사용자는 서로 다른 계정을 사용한다(NFR-11 차단 회피). |
| OQ-01 | 미결 | 도메인 OQ-01 참조: 회원 탈퇴 여부 (현재 제외). |
| OQ-02 | 미결 | 도메인 OQ-02 참조: 비밀번호 찾기/재설정 (현재 제외). 이 경우 비밀번호 분실 시 복구 수단이 없음을 인지한다. |
| OQ-03 | 미결 | (PRD 고유) 비밀번호 변경 시 다른 기기의 Refresh Token을 폐기할지 여부. 현재 세션은 유지한다. |
